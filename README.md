# Ask & Ace

**Ask your PDF. Ace your exam.**

A PDF normally just sits there. Ask & Ace brings it to life: upload one file, and it can answer
questions about itself, show you the page each answer came from, write a practice test from its own
content, and mark your attempt.

- **Ask your PDF** — ask questions in your own words. Answers are generated by an LLM from the most
  relevant passages of **your** documents and come with page-level citations. If the document doesn't
  contain the answer, it says so instead of guessing.
- **Ace your exam** — turn the same PDF into a practice test, sit it, and get marked. Each result
  links back to the page the question came from.

Both halves share one account, one document store and one index, so a PDF moves between them by id —
never by re-uploading it. The visual language comes from the ExamForge AI landing page, ported into
plain CSS rather than pulling in Tailwind.

**Stack:** FastAPI · ChromaDB · fastembed (ONNX embeddings) · any OpenAI-compatible LLM
(Groq / Gemini free tiers) · SQLite · JWT auth · React + Vite + React Router · pytest · Docker

## How it works

```
 PDF ──► extract text per page ──► chunk (≈1000 chars, 150 overlap, never crossing pages)
                                        │
                                        ▼
                         embed chunks (bge-small, 384-dim) ──► ChromaDB
                                        (metadata: user_id, document_id, filename, page)

 Question ──► embed ──► top-k similar chunks (filtered to THIS user)
                              │
                              ├─ none close enough? ──► "I couldn't find that" (LLM is never called)
                              ▼
                 prompt = numbered passages + question ──► LLM ──► answer citing [1], [2]…
                              │
                              ▼
              response = answer + sources (file, page, snippet) ──► UI shows citation chips
```

Exam generation deliberately does **not** reuse the retriever:

```
 Document ──► all its chunks ──► even-stride sampling across the whole document
                                        │   (not top-k for one query: a test must
                                        │    cover page 9 as well as page 1)
                                        ▼
            prompt = passages + count/type/difficulty ──► LLM in JSON mode
                                        │
                                        ▼
              validate every item (answer must be among its own options,
              page must exist, no duplicates) ──► drop anything unusable
                                        │
                                        ▼
                      store questions + answer key server-side
                                        │
         browser gets the questions WITHOUT the key ──► user answers ──► server marks
                                        │
                                        ▼
                  result = score + key + explanation + page ──► "revise page 3 →"
```

Key design decisions (good interview talking points):

- **Chunks never cross page boundaries**, so every chunk maps to exactly one page and citations are exact.
- **The answer key never reaches the browser.** `GET /exams/{id}` omits answers and explanations;
  the server marks a submission and only then returns the key. Nothing to read out of the DOM.
- **Generated output is treated as untrusted.** Every question is validated — an mcq whose answer is
  not one of its own options is ungradable, so it is discarded rather than stored, and the response
  says how many were dropped.
- **The request is capped to what the document can carry.** Asking for 30 questions about two
  sentences makes a model repeat itself or refuse, so the count is scaled to the available text and
  the UI explains the shortfall.
- **Cross-module handoff passes only a document id** (`/exams?doc=7`), resolved against the
  requesting user's own documents. No file contents, no base64, in the URL.
- **Overlap + word-boundary splitting** keeps sentences that straddle a chunk edge retrievable.
- **Relevance threshold before the LLM.** Chunks with cosine distance above `MAX_DISTANCE` are dropped;
  if nothing survives, the API answers "not found" without spending an LLM call. The system prompt also
  tells the model to answer only from the passages.
- **Tenant isolation.** Every vector carries `user_id`; every query filters on it. Tests cover cross-user access.
- **Prompt-injection stance.** Retrieved text is labelled as untrusted data in the system prompt. This reduces
  but does not eliminate the risk.
- **Provider-agnostic LLM client.** One small HTTP client for any OpenAI-compatible endpoint.
- **Injectable dependencies.** The app factory takes an embedder and LLM, so the 30 tests run offline and deterministically.
- **bcrypt password hashes, short-lived JWTs**, generic login errors (no user enumeration), upload size/type/page limits.

## API

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/auth/register`, `/auth/login` | – | returns a JWT |
| POST | `/documents` | ✓ | upload + index a PDF (multipart `file`) |
| GET | `/documents` | ✓ | list your documents |
| DELETE | `/documents/{id}` | ✓ | delete a document and its vectors |
| POST | `/ask` | ✓ | `{question, document_id?}` → `{answer, sources[]}` |
| GET / DELETE | `/history` | ✓ | read / clear chat history |
| POST | `/exams` | ✓ | `{document_id, count, question_type, difficulty}` → a generated test |
| GET | `/exams` | ✓ | list your tests, with question count and best score |
| GET | `/exams/{id}` | ✓ | one test, **without** the answer key |
| POST | `/exams/{id}/attempt` | ✓ | `{responses[]}` → `{score, total, results[]}` with the key |
| DELETE | `/exams/{id}` | ✓ | delete a test and its attempts |
| GET | `/health` | – | liveness |

Interactive docs: `http://localhost:8000/docs`.

## Run locally

Get a free API key from [Groq](https://console.groq.com) (or Google AI Studio for Gemini).

```bash
# backend
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env        # then set SECRET_KEY and LLM_API_KEY
uvicorn app.main:app_factory --factory --reload      # http://localhost:8000

# frontend (second terminal)
cd frontend
cp .env.example .env
npm install && npm run dev                           # http://localhost:5173
```

The first upload downloads the embedding model (roughly 100–150 MB) once.

**Indexing speed.** A 143-page, 3.7 MB PDF (211 chunks) indexes in about 6 seconds: ~1s to extract
text with pypdf and ~4.5s to embed. The server logs the breakdown for every upload, so a slow one can
be diagnosed rather than guessed at:

```
INFO:     indexed Python Programming.pdf: 143 pages, 211 chunks, batch_size=1 | extract 1.05s, embed 4.45s
```

Two things dominate, and neither is obvious:

- **`EMBEDDING_BATCH_SIZE=1` is the fast setting**, not a slow one. fastembed pads every text in a batch
  to the longest member, so large batches waste compute on padding. At 256 the same document took 19s.
- **`--reload` makes indexing look far slower than it is.** The file watcher restarts the worker and the
  ONNX model reloads, which inflated the same upload to 20–56s while measuring. Time uploads on a server
  started without `--reload`.

### Verify with the real model and LLM

```bash
python scripts/smoke_test.py http://localhost:8000
```

It registers a throwaway user, uploads a PDF, asks an on-topic and an off-topic question, and prints the
retrieval distances. **Use those numbers to tune `MAX_DISTANCE`** (default 0.65 is a starting guess, not a
measured value): it should sit above the on-topic distance and below the off-topic one.

## Tests

```bash
cd backend && pytest -q
```

97 tests: auth (hashing, duplicates, validation, no user enumeration), upload limits and malformed/scanned PDFs,
retrieval with correct page citations, "not found" without an LLM call, greetings handled without retrieval,
per-user isolation, LLM failure → 502/503, history, the chunker (overlap, page mapping, no mid-word splits), and
exams (coverage sampling, JSON recovery from fenced/chatty replies, validation and discarding, grading, the
answer key staying server-side, and cross-user access on every exam endpoint).

They use a deterministic fake embedder and fake LLM, so they run offline. They do **not** exercise the real
embedding model or a real LLM; that is what the smoke test is for.

## Deploy (free tier)

**Backend on Render:** push this repo to GitHub → Render → New → Blueprint → select the repo (uses `render.yaml`).
Set `LLM_API_KEY` and `CORS_ORIGINS` (your Vercel URL) in the dashboard.

**Frontend on Vercel:** import the repo, set *Root Directory* to `frontend`, add env var
`VITE_API_URL` = your Render URL, deploy. Then put the Vercel URL into the backend's `CORS_ORIGINS`.

Then run `python scripts/smoke_test.py https://<your-render-url>`.

## Known limitations (state these honestly in interviews)

- **Free-tier storage is ephemeral.** Render's free disk resets on redeploy and the service sleeps when idle, so
  accounts and indexes can disappear. Use a persistent disk or hosted Postgres/Chroma for real use.
- **Memory.** The embedding model plus ChromaDB may be tight on a 512 MB instance. If it OOMs, move to a larger plan.
- **Text PDFs only.** Scanned PDFs are rejected with a clear message (no OCR in this project).
- **No rate limiting, email verification or password reset.** Fine for a demo, required before real users.
- **JWT is kept in `localStorage`**, which is exposed to XSS; an httpOnly cookie is the stronger choice.
- **Short answers are graded on word overlap, not meaning.** A correct answer phrased very differently can be
  marked wrong, so the UI labels those grades as approximate and shows the expected answer next to them.
  Grading multiple choice and true/false is exact.
- **Generation is synchronous.** A 30-question request holds the HTTP connection for as long as the model takes
  (seconds in practice, with a 180 s ceiling). A background job with polling is the right shape for slower models.
- **Question quality is the model's.** Items are validated for *form*, not for pedagogical value; a question can be
  well-formed and still shallow. Regenerating is cheap.
- **Retrieval is vector-only** (no hybrid keyword search or reranking), and the distance threshold is a single global value.
- **Not load-tested**; SQLite and a local Chroma directory mean a single instance.

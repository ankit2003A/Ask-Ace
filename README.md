# DocuMind AI

Upload PDFs and ask questions about them. Answers are generated by an LLM from the
most relevant passages of **your** documents and come with page-level citations.
If the documents don't contain the answer, it says so instead of guessing.

**Stack:** FastAPI · ChromaDB · fastembed (ONNX embeddings) · any OpenAI-compatible LLM
(Groq / Gemini free tiers) · SQLite · JWT auth · React + Vite · pytest · Docker

## How it works

```
 PDF ──► extract text per page ──► chunk (≈1000 chars, 150 overlap, never crossing pages)
                                        │
                                        ▼
                         embed chunks (bge-small, 384-dim) ──► ChromaDB
                                        (metadata: user_id, document_id, filename, page)

 Question ──► embed ──► top-k similar chunks (filtered to THIS user)
                              │
                              ├─ none close enough? ──► "I couldn't find that" (LLM is never called)
                              ▼
                 prompt = numbered passages + question ──► LLM ──► answer citing [1], [2]…
                              │
                              ▼
              response = answer + sources (file, page, snippet) ──► UI shows citation chips
```

Key design decisions (good interview talking points):

- **Chunks never cross page boundaries**, so every chunk maps to exactly one page and citations are exact.
- **Overlap + word-boundary splitting** keeps sentences that straddle a chunk edge retrievable.
- **Relevance threshold before the LLM.** Chunks with cosine distance above `MAX_DISTANCE` are dropped;
  if nothing survives, the API answers "not found" without spending an LLM call. The system prompt also
  tells the model to answer only from the passages.
- **Tenant isolation.** Every vector carries `user_id`; every query filters on it. Tests cover cross-user access.
- **Prompt-injection stance.** Retrieved text is labelled as untrusted data in the system prompt. This reduces
  but does not eliminate the risk.
- **Provider-agnostic LLM client.** One small HTTP client for any OpenAI-compatible endpoint.
- **Injectable dependencies.** The app factory takes an embedder and LLM, so the 30 tests run offline and deterministically.
- **bcrypt password hashes, short-lived JWTs**, generic login errors (no user enumeration), upload size/type/page limits.

## API

| Method | Path | Auth | Purpose |
|---|---|---|---|
| POST | `/auth/register`, `/auth/login` | – | returns a JWT |
| POST | `/documents` | ✓ | upload + index a PDF (multipart `file`) |
| GET | `/documents` | ✓ | list your documents |
| DELETE | `/documents/{id}` | ✓ | delete a document and its vectors |
| POST | `/ask` | ✓ | `{question, document_id?}` → `{answer, sources[]}` |
| GET / DELETE | `/history` | ✓ | read / clear chat history |
| GET | `/health` | – | liveness |

Interactive docs: `http://localhost:8000/docs`.

## Run locally

Get a free API key from [Groq](https://console.groq.com) (or Google AI Studio for Gemini).

```bash
# backend
cd backend
python -m venv .venv && source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env        # then set SECRET_KEY and LLM_API_KEY
uvicorn app.main:app_factory --factory --reload      # http://localhost:8000

# frontend (second terminal)
cd frontend
cp .env.example .env
npm install && npm run dev                           # http://localhost:5173
```

The first upload downloads the embedding model (roughly 100–150 MB) once.

### Verify with the real model and LLM

```bash
python scripts/smoke_test.py http://localhost:8000
```

It registers a throwaway user, uploads a PDF, asks an on-topic and an off-topic question, and prints the
retrieval distances. **Use those numbers to tune `MAX_DISTANCE`** (default 0.65 is a starting guess, not a
measured value): it should sit above the on-topic distance and below the off-topic one.

## Tests

```bash
cd backend && pytest -q
```

30 tests: auth (hashing, duplicates, validation, no user enumeration), upload limits and malformed/scanned PDFs,
retrieval with correct page citations, "not found" without an LLM call, per-user isolation, LLM failure → 502/503,
history, and the chunker (overlap, page mapping, no mid-word splits). They use a deterministic fake embedder and
fake LLM, so they run offline. They do **not** exercise the real embedding model or a real LLM; that is what the
smoke test is for.

## Deploy (free tier)

**Backend on Render:** push this repo to GitHub → Render → New → Blueprint → select the repo (uses `render.yaml`).
Set `LLM_API_KEY` and `CORS_ORIGINS` (your Vercel URL) in the dashboard.

**Frontend on Vercel:** import the repo, set *Root Directory* to `frontend`, add env var
`VITE_API_URL` = your Render URL, deploy. Then put the Vercel URL into the backend's `CORS_ORIGINS`.

Then run `python scripts/smoke_test.py https://<your-render-url>`.

## Known limitations (state these honestly in interviews)

- **Free-tier storage is ephemeral.** Render's free disk resets on redeploy and the service sleeps when idle, so
  accounts and indexes can disappear. Use a persistent disk or hosted Postgres/Chroma for real use.
- **Memory.** The embedding model plus ChromaDB may be tight on a 512 MB instance. If it OOMs, move to a larger plan.
- **Text PDFs only.** Scanned PDFs are rejected with a clear message (no OCR in this project).
- **No rate limiting, email verification or password reset.** Fine for a demo, required before real users.
- **JWT is kept in `localStorage`**, which is exposed to XSS; an httpOnly cookie is the stronger choice.
- **Retrieval is vector-only** (no hybrid keyword search or reranking), and the distance threshold is a single global value.
- **Not load-tested**; SQLite and a local Chroma directory mean a single instance.
